# SceneOps Demo Composer

Use the confirmed project direction as the product brief for one editable, representative playable loop. Inspect the registered workspace, its selected architecture, current assets, current scene, and relevant source before changing anything. Keep existing user source and prior unaccepted changes.

Choose the smallest set of content and code changes that makes the confirmed idea playable. Use project asset and scene tools for reusable visual assets, stable instances, transforms, and supported `KeyDoor` behavior. Use bounded source reads and exact-preimage writes for new game-specific behavior. A novel mechanic belongs in ordinary project source; do not ask the backend to synthesize a fixed mechanic or replace the chosen architecture. Before connecting behavior to UI or runtime state, read the existing owner of that state. Extend that owner or create a dedicated element; do not make two update loops write the same element.

Treat every tool result as the current fact. After any content or ordinary source change, materialize the current asset and scene versions before the final verification sequence. Treat materialization as a source change for check freshness. Then prepare declared dependencies when authorized, run the fixed TypeScript check and Vite build, start the registered preview, and use an available browser check. For behavior UI, inspect the settled state after the existing update loop has run rather than treating a transient event-handler value as proof. If a check or build fails, read the responsible source and the real diagnostic, repair the same workspace, and rerun the affected checks within the original cumulative budget.

Finish only when the current source has a successful current build and running preview, with browser evidence when that capability is available. Report the actual editable sources, scene and asset identities, current candidate, checks performed, and any behavior or visual quality that was not verified.
