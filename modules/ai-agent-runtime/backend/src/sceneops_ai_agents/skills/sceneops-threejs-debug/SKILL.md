# 故障定位

## 适用范围

已有具体失败结果的诊断与修复。过去失败的记录不自动等于现在仍有故障；查看同一操作最新结果、源码变更和 source_stale。

## 输入事实

核对项目、卡片、worktree、实际操作和错误日志，先找第一个有因果意义的错误及所属模块。区分缺依赖、缺工具、授权不足、执行失败和结果未知。

## 工作方法

类型或构建错误先检查对应声明、导入、调用和现有版本，不升级工具链掩盖错误。输入失效追踪监听器、焦点、意图、更新次序及状态条件；动画和物理检查秒/毫秒、循环所有者、同步顺序与重开清理。
黑屏仅在实际可观察时检查 canvas CSS/缓冲区大小、上下文、渲染循环、相机投影、物体变换、灯光材质、加载路径与输出；没有浏览器工具时只分析已有代码和日志，明确哪些假设未观察。
在拥有根因的模块修复，再检查同一路径。性能问题先在相同场景测量，区分 CPU、绘制调用、像素、几何、内存、网络，再修改对应瓶颈；没有测量不承诺优化幅度。

## 常见失败

端口提供了别的项目；旧构建日志被当成新源码结果；看见文件路径就声称看过画面；修改 CSS 掩盖相机错误；删除功能或关闭检查以消除报错。

## 完成依据

报告已证实根因或仍待核查的假设、修改位置、原失败路径的复查结果。未知操作先核查，不能盲目重放；没有执行条件时保留具体限制并继续独立工作。

## 原生制作与领域回流

普通源码使用 CLI 原生读写能力；资产版本、实例变换及共享引用使用 SceneOps MCP 提供的领域工具。先读取当前版本，再带 expected_version 更新；冲突时重读并按用户意图修订。托管内容修改后调用 code.demo_content.materialize，并让实际游戏读取其生成的内容模块。不要直接编辑托管清单或虚构逐动作 JSON 调用。
